## 1. 模块定位

### 1.1 研究问题与职责

**核心问题：在题目、模型和重试预算相同的条件下，实际公开测试诊断是否比一般重试带来更多最终修复成功？**

研究负责人负责确定数据来源、定义成功标准与统计单位、核查实验覆盖和运行证据、分析整体结果及具体案例。上游由模型与验证组件产生代码、测试结果和运行摘要；本模块将它们转为指标、报告和有证据的结论，供答辩展示使用。

总体编排、模型适配与 Docker 隔离由对应负责人展开。本稿只解释影响研究口径的接口和条件。

### 1.2 主要发现

**实验结果：** 两批全量共享首轮实验中，C 相对 B 分别多成功 3 题和 5 题；精选 30 题的独立首轮实验中，B/C 最终均通过 18 题。

**研究解释：** 全量批次观察到实际诊断相对一般重试的正向差异；补充实验没有再次观察到总体优势。现有记录不足以证明反馈在所有设置下均有效，也不足以证明结果稳定或统计显著。

## 3. 当前架构

### 3.1 数据集选择与质量控制

[FeedbackEval 论文](https://arxiv.org/html/2504.06939)提供反馈驱动代码修复的研究背景。本项目采用其 **HumanEval 全部 164 题分支，每题一个冻结错误候选**；未声称复现论文全部任务、反馈类型、模型与成绩。

选择该分支的理由是：单函数任务与当前只修改 `solution.py` 的系统范围相符；已有错误候选让研究对象明确为修复；需求与可执行测试便于控制输入和验证结果。HumanEval+ 提供同一题目的扩展验证输入，不是另一套独立新题。

| 数据来源 | 使用方式 | 研究作用 |
| --- | --- | --- |
| FeedbackEval 冻结错误候选 | 复制为任务初始 solution.py | 固定修复起点 |
| FeedbackEval 冻结 HumanEval 测试 | 作为公开测试 | 支持实际反馈、决定停止 |
| HumanEval+ v0.1.10 输入 | 构建扩展隐藏验证 | 检查公开样例之外的行为 |
| 正确实现 | 用于离线构建或参考预检，不复制进修复工作区 | 检查评分依据，不给模型答案 |

## 4. 具体运行流程

### 4.1 正常路径与停止条件

1. `TaskSpec.load` 读取配置，检查题目路径和可编辑范围；正式批量入口要求三个策略、最大提交次数为 3。
2. `_benchmark_schedule` 生成任务×策略×重复编号，用 seed 打乱顺序；`_execution_units` 再按题组织共享首轮与 B/C 分支。这是执行顺序随机化，不是随机筛题。
3. A 生成首轮。B/C 继承快照；公开通过则停止修复，失败则继续，最多各追加两次。B 得到一般重试指令，C 得到实际公开测试反馈；两组都可见公开测试源码。
4. 停止后，对基线、首次、最终代码进行相应验证与比较。隐藏评分不再触发模型修复。首次隐藏字段也是停止后的离线评分，不表示首轮时向模型展示隐藏测试。
5. 最终公开和隐藏同时通过才记整题成功。保存单次摘要；每条批量结果追加写入并 `flush/fsync`，随后汇总导出。

核心成功判断，摘自 `run.py`：

```python
outcome = "passed" if final_public.passed and final_hidden.passed else "failed"
```

### 4.2 失败、异常与恢复

| 情况 | 识别与记录 | 统计或后续行为 |
| --- | --- | --- |
| 代码不满足公开或隐藏测试 | 验证失败，通常 outcome=failed | 正常失败保留在有效分母 |
| API 或执行异常中断 | RunExecutionError 或批量异常记录，outcome=error | 单列异常数量和计划覆盖 |
| 共享首轮 A 没有可复用结果 | B/C 记 shared_first_error | 不伪造分支答案，不当作两次独立调用失败 |
| 工具参数非法 | submission_rejected，单次状态可为 model_protocol_error | 不将非法内容写为新答案；不代表整个 run 必然当场结束 |
| 候选运行超时 | CommandResult.timed_out | 可成为失败验证；若抛异常中断则按 error 处理，应查实际字段 |
| 恢复执行 | 校验配置，按 task_id、strategy、repetition 跳过已有行 | failed 和 error 也会跳过，不是自动重跑异常 |

中断也可能生成部分报告，完成度必须看已记录数与计划数。四批配置均为 `repetitions=1`；最大三次提交不是完整重复三遍，顺序 seed 也不能固定全部远程生成行为。

```text
assert candidate("aaabb") == 2
```

```python
# 首轮错误条件；B 后续仍保留
ord(c) % 2 != 0

# C 第二次条件
```

讲解要点：无分隔符时应按 a=0 的字母下标判断奇偶。a 的编码为 97、b 为 98，首轮数出了三个 a，实际应数两个 b。`abcdef` 恰好两种算法都返回 3，`aaabb` 才能区分错误行为。C 第二次调整后公开与隐藏均通过，B 三次保留错误表达式。这是可追踪的正例，不单独证明全部任务或模型的普遍收益。

## 6. 图表与指标解释

### 6.1 统计单位与计算口径

一道题×一种策略×一个 repetition 构成一个 run；run 内可以有多次 attempt。164×3×1=492 条策略记录，不是 492 道不同题，也不是 492 次实际 API 调用。

| 指标 | 计算定义与注意事项 |
| --- | --- |
| 最终隐藏通过率（主效果指标） | 有效 run 中 final_hidden_passed=True 的数量／有效 run 数 |
| 整题成功比例 | outcome=passed 的数量／有效 run 数；要求最终公开且隐藏通过，本包与主指标数值一致 |
| 有效分母 | passed 和 failed 均保留；error 单列，同时报告计划覆盖 |
| 条件隐藏修复率 | 在共同首轮公开失败群体中，最终隐藏通过数／群体数；不直接套用到独立首轮批次 |
| B/C 配对差 | 同题同 repetition 的 I(C隐藏通过)−I(B隐藏通过) 的平均值，只用两组均有效配对 |
| 公开/隐藏差距 | 最终公开通过率−最终隐藏通过率 |
| 隐藏改善与回归 | 首次隐藏失败→最终通过为改善，首次通过→最终失败为回归；默认按全部有效 run 计比例 |
| 测试函数修复/回归 | 明确 failed→passed / passed→failed；error、timeout、not_run 不作普通断言比较 |
| 用量 | 分开报告策略等价成本、增量成本和整批实际成本；缺价格或完整用量时保留 N/A |

有效分母源码：

```python
valid = [row for row in all_rows if row.get("outcome") in {"passed", "failed"}]
```

## 7. 汇报讲稿

### 7.1 研究问题与数据选择

老师好，我负责数据集选择、指标设计、实验核查和案例分析。我主要回答：在题目、模型和重试预算相同的条件下，实际测试诊断能否比一般重试修好更多题，以及这个结论适用于什么范围。

主实验采用 FeedbackEval 的全部 164 道 HumanEval 任务，每题固定一个错误实现。选择它，是因为我们的系统处理单函数修复，题目有明确需求、错误起点和可执行测试。这里的“全量”是 HumanEval 分支，不是整篇论文的全部数据和设置。

公开测试来自 FeedbackEval，扩展隐藏输入来自 HumanEval+，版本为0.1.10。公开测试帮助修复和决定停止，隐藏测试在修复结束后独立验收。正确实现、预生成反馈和隐藏诊断都不提供给修复模型。

已有预检记录显示：164 个错误候选全部公开失败，164 个参考实现全部隐藏通过。这是题目质量检查，不是模型成绩。数据处理也有披露：57 和 105 题替换过候选，32 题移除了 7 个参考实现不能稳定通过的输入，题目仍保留。本次核对了这些记录，没有重新执行全题预检。

### 7.2 对照条件与指标口径

两批全量实验采用共享首轮。A 生成第一份修复代码，B、C 继承同一份代码；公开失败时，两组各最多追加两次。B 只得到一般重试指令，C 得到真实公开测试诊断。两组本来都能看到公开测试源码，所以比较的是实际执行诊断的增益。

这使我们能区分：A 到 B 的改善包含多尝试的作用；C 对 B 才是反馈收益的主要比较。本次核对了 DeepSeek 的 164 题和 Qwen 的 160 道有效题，三组首轮代码哈希全部一致，日志也记录了继承关系。

统计单位也需要固定：一道题、一种策略、一个重复编号构成一次运行；运行内部可以有多次提交。所以 164 题乘三策略得到 492 条策略结果，配对比较按同题、同重复编号进行。

整题成功要求最终公开和隐藏同时通过。主指标是有效运行中的最终隐藏通过率；这些记录里，隐藏通过的运行也全部公开通过。

分母同时保留成功和正常修复失败，连接等异常单列。例如 Qwen 每组计划 164 次，4 道首轮连接异常，各组有效 160。C 成功 143 次，主要比例就是 143 除以 160，约百分之八十九点三八，同时报告每组 4 个异常，不能把异常隐藏掉。

### 7.3 实验记录与全量结果

实验入口生成任务、策略和重复编号，单次运行保存代码与测试摘要，汇总函数计算指标，报告函数输出表格和图表。我从配置确认计划与协议，逐条重算结果，再用摘要、事件日志和提交快照交叉核查。本次复核了四批记录，相关六个测试文件共 50 项通过.

先看 DeepSeek 全量批次。A、B、C 最终分别通过 142、145、148 题，分母都是 164。B 比 A 多成功 3 题，C 比 B 再多 3 题，后者增加一点八三个百分点，不能把 C 对 A 的全部改善都归给反馈。

整体成绩还会被大量首轮已通过题稀释。DeepSeek 首轮公开通过 152 题，只有 12 题进入后续修复。在共同失败群体里，B 最终隐藏修好 3 题，C 修好 6 题，分别是百分之二十五和百分之五十。这是 12 题子集的比例，不能说全题库提升了二十五个百分点。

Qwen 完整计划批次中，A、B、C 分别通过 131、138、143 道有效题。C 比 B 多 5 题，增加三点一三个百分点；共同首轮公开失败的 18 题里，B 隐藏修好 7 题，C 修好 12 题。

资源统计也要符合协议。DeepSeek 全量实际调用 200 次：A 的 164 次，加上 B 追加 19 次、C 追加 17 次。共享首轮不能重复算成三份真实请求；金额缺少依据时保留未知。

Qwen 的四道首轮连接异常还会传播到 B、C，因此三组合计十二条错误记录，不代表十二次独立网络故障。异常需要按根源解释，不能混作代码逻辑失败。

### 7.4 正反案例：收益与覆盖限制

正例是全量批次的第 125 题 split_words。无分隔符时，它要统计从 a 等于零开始、字母下标为奇数的小写字符。输入 aaabb 应该数两个 b，结果是 2。

B、C 相同的首轮代码却判断字符编码的奇偶。a 的编码是 97，b 是 98，所以它数了三个 a，得到 3。公开反馈明确指出期望 2、实际 3。

这个错误对 abcdef 恰好也返回 3，和正确结果相同；而 aaabb 的不对称输入才暴露了问题。这说明测试的价值取决于是否区分了错误实现与正确行为，不只是样例数量。

B 三次提交都保留这个错误表达式。C 收到反馈后，第二次先减去 a 的编码，再判断奇偶，让 a 对应零、b 对应一。随后公开和隐藏都通过。这个案例对应了相同首轮、实际诊断、针对性修改和最终评分；但一个正例不能证明所有题都受益。

反例是补充批次第 154 题。模型第二次公开通过，但隐藏日志报告第 64 个输入失败。核对输入常量和代码，发现两个空字符串触发了空枚举范围，any 返回 False，遗漏了边界条件。这是结合代码与输入的分析，不是日志直接给出了完整原因。

公开与隐藏的差距也体现在整体成绩：DeepSeek C 公开通过 160 题，隐藏只通过 148 题。因此公开通过不能当作最终成功；隐藏失败也不能再交回模型，修好后覆盖这次成绩。

### 7.5 补充实验与结论边界

之后精选的 30 题依据历史结果选择，覆盖持续困难、策略敏感等类别，适合压力分析，但不是无偏随机样本。这批三组独立生成首轮，不继承 A 的答案，与全量协议不同。

结果是 A 通过 12 题，B、C 都通过 18 题。C 在 125 题独赢，B 在 154 题独赢，净差为零。所以补充实验没有再次观察到反馈的总体优势，不能只因为 C 公开多过一题，就说最终修复更好。

另有一批未完成 Qwen 实验，记录 400 条、计划 492 条，B、C 隐藏通过分别为 114、113。我们将它单列披露，不作为完整全量成绩，也不因方向不同而删除。

因此，我们观察到两批全量共享首轮中反馈的正向差异，也观察到补充独立运行中的持平结果。四批都只有一次 repetition，最多三次提交不等于重复实验三遍，现有记录不能证明收益已经稳定或统计显著。本包也没有支持 Qwen 零点五 B 或“30 题修复率百分之百”的对应证据。

我的工作是把数据来源、指标分母、运行记录和正反案例对应起来，让观察到的收益和限制都有依据。进一步验证稳定性，需要在固定数据和同一协议下做多次重复。谢谢老师。
