模型接口与修复协议层



1\. 模块定位



· 一句话说明：负责将任务与诊断反馈安全地组装为提示词，约束大模型的输出格式，并控制 A/B/C 三组实验的修复重试循环。

· 上游与下游：上游接收来自 run.py::RunService.execute 的任务参数与工作区快照；下游将模型生成的代码落盘后，交由 sandbox.py::DockerSandbox 进行隔离测试。

· 解决的问题：解决大模型在执行修复任务时的“上下文盲区”、“格式不可控”以及“如何利用报错反馈进行自我修正”的问题。



2\. 源码结构



· 入口文件和入口函数：

&#x20; · 重试循环与 Prompt 拼装：src/repair\_assistant/agent.py 中的 TestDrivenRepairAgent.run() 和 \_attempt\_prompt()

&#x20; · 模型 API 调用与解析：src/repair\_assistant/model.py 中的 OpenAICompatibleAdapter.complete()

· 核心类与函数：

&#x20; · TestDrivenRepairAgent：负责控制修复循环的停止条件、动态拼装提示词、以及异常捕获。

&#x20; · \_model\_submission：负责接收模型返回的 JSON，校验格式，并将代码写入 solution.py。

&#x20; · OpenAICompatibleAdapter：统一封装了 DeepSeek 和通义千问等模型的 API 调用。

· 关键数据结构：

&#x20; · submit\_solution：通过 Function Calling 定义的工具，强制模型将代码放入 content 字段。

&#x20; · RepairStrategy（枚举）：定义了 SINGLE\_SHOT (A组)、RETRY\_WITHOUT\_FEEDBACK (B组)、TEST\_FEEDBACK (C组) 三种策略。

· 对应测试：通过沙盒验证的 PublicVerifier，以及 tests/ 目录下的协议解析测试。



3\. 当前架构



一句话定位



模型在沙盒之外，仅通过文本和工具协议与系统交互，受控地生成修复代码。



在整体系统中的位置



上游是 run.py，通过传入 strategy 和 task 状态，向本模块提供输入。



本模块从 agent.py::run 开始执行，内部主要经过：



1\. \_attempt\_prompt()：拼装当前代码、题目、公开测试，C组额外注入报错。

2\. ModelAdapter：调用云端 API 获取模型的 submit\_solution 调用请求。

3\. \_model\_submission()：提取代码并校验写入。



执行完成后产生更新后的 solution.py，交给 run.py 调度沙盒进行测试。



核心代码说明



· agent.py 中的 SYSTEM\_PROMPT 变量：限制模型权限，告知隐藏测试不可用。

· agent.py 中的 \_attempt\_prompt 函数：核心！根据 A/B/C 策略控制是否将 feedback 报错注入输入。

· agent.py 中的 \_model\_submission 函数：拦截 model\_protocol\_error 异常，确保只有合法代码落盘。

· model.py 中的 OpenAICompatibleAdapter 类：设置 tool\_choice 强制模型必须调用 submit\_solution。



关键数据说明



· previous\_feedback：包含上一轮的 stdout / stderr，C 组重试时作为诊断信息拼入 Prompt。

· solution.py：纯代码文本，是唯一允许模型修改的文件。

· RepairStrategy：A/B/C 策略枚举，控制循环次数和反馈逻辑。



设计原因



当前设计主要解决模型幻觉和实验公平性问题。

代码中的具体体现是：



· 防越权：由 agent.py 的 SYSTEM\_PROMPT 限制模型不能执行命令。

· 格式约束：由 model.py 的 tool\_choice 强制模型以 JSON 格式提交代码。

· 实验对照：由 agent.py::\_attempt\_prompt 确保 B 组得不到报错，C 组能看到报错。



4\. 具体运行流程



流程入口



入口为 agent.py::TestDrivenRepairAgent.run(task)。

调用它的是 run.py::RunService.execute，传入的主要参数包括：



· strategy：策略枚举（A组只跑1次，B/C组跑3次）。

· shared\_first：B/C 组继承的 A 组首轮代码。



步骤 1：动态拼装输入



调用代码：agent.py::\_attempt\_prompt



· 输入：当前代码、题目、测试用例、上一轮报错（如果有）。

· 处理：判断当前策略。如果是 C 组且 previous\_feedback 不为空，将报错追加到 Prompt 末尾；如果是 B 组则不追加。

· 输出：完整的 messages 数组，发给模型。



步骤 2：API 调用与输出拦截



调用代码：model.py::complete 和 agent.py::\_model\_submission



· 输入：API 返回的 JSON 数据。

· 处理：检查是否有 tool\_calls，且名称必须为 submit\_solution，提取 content 字段。如果格式不对，抛出 model\_protocol\_error。

· 输出：将合法代码写入 workspace/solution.py。



停止条件



流程会在以下情况下停止：



· 成功：沙盒返回的 VerificationResult.passed 为 True（公开测试通过）。

· 次数限制：A 组 1 次即停；B/C 组达到 max\_attempts = 3 停止。

· 协议错误：模型未按规定格式输出，视为本次尝试失败，消耗一次重试次数。



分支逻辑



· A/B/C 的核心差别发生在 agent.py::\_attempt\_prompt：仅当 strategy == 'TEST\_FEEDBACK'（C组）时，才拼接 \_feedback() 产生的 pytest 报错。

· 异常流程：如果 API 超时或网络异常，run.py 会捕获异常，记录为 model\_error 并保存事件日志。



5\. 演示方案



演示目的



说明测试反馈（C组）如何帮助模型修正错误，以及输出协议约束如何保证代码安全落盘。



选择这个案例的原因



070 任务（交替取数）能最直观地展现：B 组无报错原地打转，C 组看到报错后精准修改了逻辑。



案例信息



· 任务 ID：070

· 模型：DeepSeek

· 策略：B组（无反馈重试） vs C组（带报错重试）

· 最终状态：B组隐藏失败，C组通过。



演示顺序



1\. 打开网页报告第 15 页（070 成功案例）。

2\. 指出 B 组代码 switch 逻辑错误，重试 3 次仍输出 \[4, 1, 3, 2]。

3\. 指出 C 组输入：报错信息 At index 0 diff: 4 != 1 被拼进了 Prompt。

4\. 对比 C 组第二次提交的代码：加入 not 修正了逻辑。



案例结论及边界



本案例直观证明了提供具体的报错日志，能有效引导 DeepSeek 模型定位并修复代码逻辑。但该结论不能过度推断为所有小模型（如 Qwen 0.5b）都能利用反馈，小模型往往在协议遵循阶段就已失败。



6\. 图表与指标解释



小模型输出协议不稳定（Qwen 0.5b 踩坑）



· 对应日志字段：agent.py 中的 submission\_rejected 或 model\_protocol\_error。

· 现象说明：早期测试中，Qwen 0.5b 无法稳定按照 submit\_solution 的 JSON 格式输出，经常输出纯文本导致解析失败。

· 结论限制：工程实践中，小模型的指令遵循能力不足会导致大量 model\_protocol\_error。这说明它的失败在于输出协议不稳定，而非代码推理不行。不能把工具格式错误和代码逻辑错误混为一谈，这也是最终切换至 DeepSeek 的核心原因。
