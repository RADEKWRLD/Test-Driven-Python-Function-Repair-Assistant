# 沙盒执行与独立测试验收

## 一、研究问题与我的职责

本课题研究一个具体问题。模型第一次提交的函数有错时，把公开测试的失败原因告诉它，能否帮助它修好同一题，并通过此前未见的测试？

我负责这项比较的执行与判定。每次提交在相同限制下运行，模型只能修改候选函数。公开测试决定是否继续修复，隐藏测试在修复结束后独立评分。每次判定都关联到题号、提交版本和逐项测试结果。这样，遇到一道失败题，可以查清是代码答错、执行超时，还是评测环境出了问题。

## 三、候选代码的权限与资源边界

宿主是运行修复助手的 Ubuntu/WSL2。它调用 DeepSeek，用请求头提交 API 密钥，接收候选代码并写入本题工作区。容器从只读工作区加载这份代码，执行 pytest，将结果返回宿主。模型服务需要联网，函数测试完全可以离线完成。两项工作由不同进程承担，密钥和个人文件留在宿主。 [模型请求](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/model.py#L105) · [运行编排](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/run.py#L127)

| 边界 | 项目中的具体设置 | 对评测的作用 |
| --- | --- | --- |
| 网络和文件 | 容器关闭外部网络，根文件系统和本题工作区只读。修复阶段只挂载本题工作区，评分时按需增加只读隐藏测试目录。项目根目录、`.env`、个人目录和 Docker 控制接口均不挂载。 | 候选代码能够读取待测函数和本阶段的测试，无法通过工作区改写题库或读取宿主密钥。 |
| 权限和临时写入 | 容器以项目运行用户的 UID/GID 执行，移除 Linux 附加能力并禁止提权。`/tmp` 提供 64 MiB 临时内存空间，禁止直接执行其中的文件。 | pytest 能写入临时评分报告，候选代码对宿主目录和系统文件的写权限受到限制。 |
| 计算资源 | 每个容器默认最多使用相当于 1 个 CPU 的计算配额、512 MiB 内存、128 个进程或线程。 | 即使某个函数大量计算、分配内存或创建进程，它能占用的资源也有上界。A/B/C 使用相同预算。 |
| 执行时间 | 每次 pytest 命令默认限时 120 秒。达到时限后容器内终止该命令，宿主最多再等待 5 秒接收结果。 | 死循环不会无限占用这一轮评测。限时针对一次测试命令，整道题还包括模型调用和多次独立评分。 |

隔离参数由宿主统一设置。公开测试运行前后，评测器还对照 SHA-256 文件指纹和可修改文件清单。测试文件被增删改，或出现未经允许的文件变更，该次公开验证即判失败。 [Docker 隔离设置](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/sandbox.py#L30) · [测试文件校验](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/verifier.py#L19)

## 四、公开测试决定何时停止，隐藏测试决定如何验收

1. **建立本题工作区。** 读入题意、错误函数和测试配置，保存原始函数快照。公开测试随工作区复制，隐藏测试单独存放。模型可见题意、当前函数和公开测试，通过唯一提交接口更新 `solution.py`。
2. **按策略处理公开结果。** A 组提交一次后直接评分。B、C 组每轮执行相同的公开测试，通过就停止，失败且有预算则继续，最多各提交三次。B 组收到重新生成的要求。C 组同时收到本轮公开测试的失败输出。B、C 的对照由此区分“多试一次”和“多试一次并获得诊断”。
3. **修复结束后独立评分。** 首次和最终提交分别评估公开与隐藏测试。只有一次提交时复用其结果。原始函数也做一次隐藏评分，用来识别原本正确的行为是否被改坏。隐藏用例和评分详情只留在评测端，模型没有根据隐藏结果继续作答的机会。
4. **保留可复查的判据。** 整次运行成功要求最终公开和隐藏测试都通过。每轮代码有快照，过程日志保留公开诊断，逐题摘要保存首次及最终结果。最终评分逐项核对预期测试与 pytest 报告，报告缺失或有应测项目未执行时，不能判全通过。 [策略分支](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/agent.py#L122) · [独立评分](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/run.py#L207) · [测试报告完整性](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/cases.py#L51)

## 五、超时、失败与回归怎样计入结果

| 现象 | 处理与统计 |
| --- | --- |
| 函数返回错误结果 | 记录失败的测试函数。公开失败时按组别和剩余预算决定是否再试，隐藏失败只进入评分。正常用尽预算的题保留在有效运行分母。 |
| 候选代码执行超时 | 终止该次命令，保存退出码、耗时和已有输出。已识别的超时单独标记，未完成的测试不计通过。B、C 组仍按原预算决定是否重试。 |
| Docker 启动或模型服务异常 | 单列基础设施错误，保留错误阶段和日志，从策略通过率的有效运行分母中排除。 |
| 修好一个用例，却改坏另一个 | 按同名隐藏测试逐项比较“原始→最终”和“首次→最终”。例如原来能处理空列表，修复后该断言失败，就是一项功能回归。总通过数即使相同，也可能同时存在修复和回归。 |

**限时生效与超时率计数有一处实测差异。** 我在同一项目沙盒中将一次受控测试的时限设为 1 秒，让命令等待 3 秒。命令约 1.08 秒后终止，退出码为 137，程序记录的 `timed_out` 为假。当前实现会将退出码 124 或宿主等待超时明确标为超时，本次 137 未计入。因此，报告中的超时率按“有效运行中被程序标记过超时的比例”解读。 [超时处理](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/sandbox.py#L115) · [回归与分母计算](Test-Driven-Python-Function-Repair-Assistant/src/repair_assistant/evaluation.py#L28)

**评价修复效果采用整题隐藏通过率。** 分子是最终提交通过该题全部隐藏测试的有效运行数，分母是该组有效运行数。比较反馈作用时，取同一题、同一重复轮次下 B、C 均有效的记录，报告两组最终隐藏通过率之差及配对数。这样可以把整体修复效果与单次测试的通过个数区分开。

## 六、案例分析 | 普通空格全对，为什么仍未修好？

**题目与判定。** 项目演示题 `public-pass-hidden-fail` 要求把字符串中每一段连续的 Unicode 空白转换为一个普通空格，同时去掉首尾空白。为验证评测规则，我在真实 Docker 中按 C 组流程固定提交了仓库自带的错误实现。一次提交后，公开 **5/5**、隐藏 **0/5**，最终判定修复失败。 [题目规范](Test-Driven-Python-Function-Repair-Assistant/benchmarks/tasks/public-pass-hidden-fail/task.json) · [本次评分摘要](Test-Driven-Python-Function-Repair-Assistant/results/sandbox-demo/runs/group_c/20261123_001/summary.json)

**缺陷在哪里。** 候选函数先去除首尾空白，再按单个普通空格拆开，最后用普通空格拼回。拆分时两个相邻分隔符会留下一个空字符串，拼接又把原来的空格数量还原。制表符、换行和其他 Unicode 空白也不会被这个分隔符识别。函数实际只完成了“去首尾”，遗漏了“归并词间空白”。 [固定候选实现](Test-Driven-Python-Function-Repair-Assistant/benchmarks/tasks/public-pass-hidden-fail/workspace/solution.py)

| 测试 | 输入 | 规范要求的输出 | 候选函数输出 | 判定 |
| --- | --- | --- | --- | --- |
| 公开 · 空串 | 空串 | 空串 | 空串 | 通过 |
| 公开 · 单词 | `hello` | `hello` | `hello` | 通过 |
| 公开 · 单空格 | `hello␠world` | `hello␠world` | `hello␠world` | 通过 |
| 公开 · 开头空格 | `␠hello` | `hello` | `hello` | 通过 |
| 公开 · 结尾空格 | `world␠` | `world` | `world` | 通过 |
| 隐藏 · 连续空格 | `a␠␠␠b` | `a␠b` | `a␠␠␠b` | 失败 |
| 隐藏 · 制表符 | `a\tb` | `a␠b` | `a\tb` | 失败 |
| 隐藏 · 换行 | `a\nb` | `a␠b` | `a\nb` | 失败 |
| 隐藏 · 混合空白 | `␠␠a␠\t\n␠b␠␠` | `a␠b` | `a␠\t\n␠b` | 失败 |
| 隐藏 · Unicode 宽空格 | `a\u2003b` | `a␠b` | `a\u2003b` | 失败 |

表中 `␠` 表示一个普通空格，`\t`、`\n`、`\u2003` 分别表示制表符、换行和 U+2003 宽空格。 [公开测试](Test-Driven-Python-Function-Repair-Assistant/benchmarks/tasks/public-pass-hidden-fail/workspace/tests/test_public.py) · [隐藏测试](Test-Driven-Python-Function-Repair-Assistant/benchmarks/tasks/public-pass-hidden-fail/hidden_tests/test_hidden.py)

**为什么没有第二次提交。** 五个公开用例都满足“去首尾后，内部已经是标准格式”这个条件，因此错误实现也能全部通过。C 组随即按规则停止，详细失败反馈没有触发。随后独立评分才暴露词间空白缺陷。 [逐轮事件记录](Test-Driven-Python-Function-Repair-Assistant/results/sandbox-demo/runs/group_c/20261123_001/events.jsonl)

**同题复核。** 我另起一次独立运行，提交按任意连续空白分词、再用一个普通空格连接的固定正确实现。用同一镜像和同一组测试，公开仍为 **5/5**，隐藏由 **0/5** 变为 **5/5**。这组对照定位了公开样例漏掉的要求，也说明隐藏测试确实能区分两份行为不同的程序。两次运行均由固定候选驱动。 [正确实现的评分摘要](Test-Driven-Python-Function-Repair-Assistant/results/sandbox-demo/runs/group_c/20261123_002/summary.json)

## 七、30 道试跑揭示了什么，为什么选用 164 道

团队先在 **30 道 HumanEval 题**上试跑 DeepSeek，首次提交 **30/30 同时通过公开和隐藏测试**。由于公开通过即停止，这次试跑没有产生“首轮失败→读取诊断→再次提交”的过程。它说明这批题对该模型缺少观察反馈作用的机会。小模型 Qwen 0.5B 又出现提交不稳定，使测试结果同时受到输出格式的影响。

团队据此查阅面向代码修复的 FeedbackEval，选定其 **HumanEval 部分全量 164 道**作为核心数据集。实验从确定的错误函数出发，让 A、B、C 在同题、同模型、同资源限制下分别运行。每题每组一轮对应 492 次运行，反馈收益由 B、C 的同题隐藏评分给出。30 题试跑在本报告中用于解释这项设计选择。 [FeedbackEval 论文第一版，第 6 节](https://arxiv.org/html/2504.06939v1)
