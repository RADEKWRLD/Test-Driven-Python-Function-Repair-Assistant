# FeedbackEval 借鉴与本课题适配

本项目借鉴本机 FeedbackEval 仓库提交
`bd8d8aefbc2319e9fdab5b1b85091b0665a48e50` 的实验组织方式，但不直接复制其执行器。
该仓库根目录未提供许可证，因此这里只记录公开可观察的实验行为与等价适配关系。

## FeedbackEval 如何测试

HumanEval 数据的每条记录包含需求、一个或多个错误候选、测试代码、正确实现和若干预生成反馈。
每个错误候选由 `RepairCandidate` 保存当前代码与 `repair_history`。第 1 轮使用数据中已有的指定反馈，
后续轮次根据当前候选重新生成反馈；模型输出 `<repaired_code>` 后立即执行测试，通过便从活动候选中移除，
否则继续，默认最多 3 轮。

HumanEval 路径把候选代码与同一条记录的测试文本拼接，写入宿主机临时文件，再调用 pytest。
进程退出码 0 或 5 被视为成功。测试失败输出会作为 `test_feedback`，并截断到约 5000 字符。
任务默认通过线程池并发执行。

## FeedbackEval 如何保存与评分

结果按模型、数据集、单轮/多轮和反馈类型保存为 JSONL。每个候选的 `repair_history` 记录轮次、
生成代码、该轮反馈和是否通过。`ProgressiveCache` 每完成一道题就追加写入，并按任务 ID 跳过已有结果。

多轮评分把每轮新通过的候选数累加，得到第 1、2、3 轮后的累计通过率。其实现只把每轮均有非空
生成代码的候选计入分母，可能排除格式错误或空输出；同时 HumanEval 的反馈测试与最终评分使用同一套
测试，因此不能衡量公开测试之外的泛化。

## 本项目采用的部分

- 每次提交保存完整代码快照、模型输入输出、公开测试结果与实际 token/耗时。
- 公开测试通过即停止，最多 3 次总提交。
- 保存 `public_pass_by_attempt` 与 `first_success_attempt`，报告第 1、2、3 次提交后的累计公开通过率。
- 每个 run 完成后立即追加到 `results.jsonl`，支持按题目、策略和重复编号继续执行。
- 额外生成 `feedbackeval-repair-histories.jsonl`，沿用 `_id / repair_results / repair_history`
  的展示层级，同时附加策略、重复编号和独立隐藏结果。
- 报告首次与最终隐藏通过率、反馈组相对无反馈重试组的同题差值，以及每成功 run 的 token。
- 正式题库使用完整 164 道 HumanEval；FeedbackEval 基础测试提供公开反馈，HumanEval+ v0.1.10 扩展测试只做最终隐藏评分。仅按官方参考预检剔除 HumanEval/32 的 7 个数值病态输入，不根据待测模型成败筛题。
- A 组生成一次共享首轮。公开失败后把同一个 `solution.py` 快照分叉给 B/C，各最多追加两次，以消除首轮模型采样差异。

## 为满足课题要求而替换的部分

- FeedbackEval 的宿主机临时执行替换为无网络、受资源限制的 Docker 执行。
- 模型没有 shell，只能调用 `submit_solution` 覆盖既有 `solution.py`；测试及其他文件不可修改。
- 公开测试用于停止与反馈；物理隔离的隐藏测试只在修复流程结束后评分，不反馈给模型。
- A/B/C 分别表示共享单次提交、从共享失败补丁无诊断重试、从同一补丁按测试反馈修复，而不是比较六种反馈生成器。
- 所有正常失败、超时和格式错误保留在主指标分母；基础设施异常单独报告，不通过删分母提高分数。
- 不把正确实现、预生成专家反馈或隐藏测试内容放进模型上下文。
- 隐藏精确答案以跨 Python 版本稳定的 SHA-256 摘要保存；浮点容差题保留压缩期望值。164 个官方参考实现必须全部通过隐藏预检。

因此，正式实验复用了 FeedbackEval 的“反馈—修复—测试—继续/停止—逐轮汇总”结构，
但测试安全、公开/隐藏划分和统计分母以课程题面为准。
